## 2. Sync and registration
- **Sync** (ego-motion): thermal is 120–154 ms behind day, constant (10_xx sessions agree within ~1 frame); the 09_06/09_07/09_09 sessions show a 1–6 ms/s drift that equals their container fps error (30.19 vs 30.0). Sync failed on 08_58_15 (2 clear windows, −143 ms), 09_58_37, 10_00_40, 10_05_11, 10_12_48, 10_15_28 (low motion): used the measured or median offset.
- **New rig geometry:** the thermal view lies *inside* the day view (≈ 3.3 day px per thermal px at the registered scale 0.30; old rig had the day view inside the thermal). `calibrate` assumed the old layout (every candidate skipped): added `coarse_search_inside`.
- 8 sessions calibrated themselves; **their solved transforms agree: 26 segments over 6 sessions give scale 0.3005 ± 0.001, rotation 0.15° ± 0.1, translation (−253, −41) ± 2 px** (the rig is rigid). Sky-dominated clips cannot calibrate (edges need structure), so those use the median transform (`make_shared_registration.py`: 08_58_15, 09_06_16, 09_07_28, 09_09_29, 09_58_37, 10_00_40). Visual check (RGB | thermal | RGB edges on thermal) on six sessions incl. shared-H ones: horizon, roads and path junctions coincide. Every extracted pair is still alignment-checked.
- Added calibration time windows (`--t-min/--t-max`) so long sessions are sampled in their usable part.

## 3. Labels: two independent detectors on a registered pair
- RGB: production day model (`yolo26s_20260921_145030_rgbcurrent.pt`), tiled 640 px / 0.2 overlap (SAHI-style, 32 tiles per 4K frame), every 3rd day frame. THERM: current best thermal model (YOLO26s-P2 seed 1).
- Per thermal frame (`build_boson_labels.py`): **pos** = RGB candidate (uav/airplane ≥ 0.10) and THERM (≥ 0.20) on the same object, box = the thermal box; **hard** = RGB ≥ 0.50, THERM silent; **neg** = no RGB ≥ 0.25 and no THERM ≥ 0.10; **skip** otherwise. Precision of the pos rule on hand-reviewed 06-23 s1 boxes was 99.5%.
- First sessions: 09_06_16 → 210 pos / 341 hard / 262 neg / 410 skip of 1,223 frames. Visual check: pos boxes sit on real fixed-wing drones down to a few pixels; hard boxes sit on empty haze (probably RGB false alarms or thermal-invisible targets): not used for training, queued for review.
- **Held-out test sessions: 08_58_15 and 10_15_59** (never in any training set). Caveat: their pos/neg labels come partly from the thermal model, so they cannot rank models against each other; the unbiased test on them is **human labels (tomorrow, queue page)**.

- Pasting still uses old-camera sprites; sharper new-camera sprites exist (627 confirmed frames) and should be used for new-camera backgrounds.
- Generator: one model trained on two cameras; evaluated separately per camera (old test 230 pairs / held-out Boson 218 pairs).
Open question for Daniel: which thermal camera is the deployed one? If the new one, weight it up (oversample ×3, new-camera sprites).

**Labeling aid (Daniel: "unsure = I think there is a drone but can't find it"):** `gt_boxes.py review --gate` draws a search circle from the nearest frames already labelled drone (constant velocity; both neighbours → interpolation, one side → extrapolation or hold) and lists in-gate candidates first. Leave-one-out on existing labels: true centre inside the circle in **88% (0715), 94% (0730), 80% (07-02 s1)** of frames, median radius 30–32 px of a 640×512 frame. Two-pass use: label what is visible, skip the rest, rerun with `--verify --only unlabelled --gate`.
